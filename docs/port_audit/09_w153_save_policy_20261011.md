# W153 / P2-04 — Godot 저장·강제 종료 안전성 검증 (2026-10-11)

## 목표와 비교 기준

- **목적:** 고정 웹 프로토타입을 완전히 Godot로 옮기고 검증·백업 후 웹 저장소를 폐기한다. 이 문서는 그중 저장 안정성만 다룬다.
- 고정 원본 `gamja121/necromancer-dice-board/reference/html-final@e13d5149fcecc802e5d626f3bef6e5daecd3d66c`, `v2-run-state.js`: IndexedDB 트랜잭션, `revision` 검사, 읽기/커밋 충돌 판정 및 복구용 `backups`.
- Godot `systems/run_session.gd`: 게임 실행 중 한 개의 `world` 인스턴스를 수정하고, 단일 파일 `user://map_run_v1.json`에 `snapshot()`을 임시 파일로 기록 → `flush()` → 원본 파일에 rename. `persist_change(before)`는 저장 실패 시 이전 스냅샷과 전투 체크포인트를 복원한다.
- **동등하게 보장하려는 목적:** 어느 시점에 종료되어도 완료된 행동은 복원되고, 아직 커밋되지 않은 행동·결과는 적용되지 않으며, 이동·사건·전투 결과의 동일 영수증이 두 번 소비되지 않아야 한다.
- **의도적인 엔진 구현 차이:** 브라우저 IndexedDB의 `revision`/여러 탭 충돌 검사를 그대로 구현하지 않는다. Godot에서는 **한 원정 저장 파일에 활성 작성자 한 프로세스**를 운영 가정으로 사용한다. 다른 게임 인스턴스가 같은 세이브 파일을 *동시에* 수정하면 충돌을 막는 운영체제 잠금/CAS는 현재 없다. 따라서 다중 인스턴스 동시 쓰기 안전성까지 검증했다고 표기하지 않는다.

## 독립 Godot 프로세스 검증

`.github/workflows/story-state-regression.yml`의 `W153 independent-process save crash before rename, commit and safe restart` 단계에서 한 CI job 내 Godot **여섯 개 이상의 개별 프로세스**를 순서대로 실행한다. 테스트 파일은 `user://w153_crash_boundary_integration_v1.json`이고, 실제 사용자 저장 경로는 건드리지 않는다.

1. `seed`: 정상 새 게임, 원본과 같은 사건 플래그, 실제 `prepare_map_roll()`에 따른 미완료 이동 상태를 커밋.
2. `crash_before_replace`: 기존 원본을 보존한 상태에서 `.tmp`에 불완전 JSON을 작성·flush한 뒤 `OS.kill(OS.get_process_id())`로 실제 테스트 프로세스를 강제 종료. `DirAccess.rename_absolute()` 이전 종료를 재현.
3. `verify_old_commit`: 새 Godot 프로세스에서 원본 플래그와 미완료 이동 복원, 부정확한 `.tmp` 무시, 동일 이동 재굴림 차단 확인.
4. `crash_after_commit`: 미완료 이동 확인을 커밋하고 새 플래그를 저장한 **다음** 즉시 Godot 프로세스 강제 종료.
5. `verify_new_commit`: 별도 프로세스 재실행 후 새 플래그·이동 확정·중복 행동 방지 확인. 재차 불러온 다음에도 동일함을 확인.
6. `cleanup`: 테스트 파일만 삭제. 별도의 기존 회귀검사에서 사건 결과 재시작·전투 롤·전투 체크포인트·저장 실패 롤백 등을 검사.

**검증 범위 제한:** Github-hosted Linux headless Godot에서 프로세스 경계/강제 종료를 검사한다. Windows Native 실제 GUI의 파일 rename 동작, 다중 실행 인스턴스 경합, 하드웨어 전원 차단/디스크 자체 손상은 별도 검증 범위다. 또한 게임 전체 새 원정→보스/스토리→다음 바퀴 E2E는 P4에서 진행한다.
